# 0008: JSON API design

**Status:** accepted

## Context
The UI (Phases 6-7), scripts, and CI integrations all need the same operations: upload logs, follow
analysis, browse results, compare runs, record triage decisions, and export.

## Decision
A REST API under `/api`, documented automatically at `/api/docs` (OpenAPI generated by FastAPI from
typed pydantic models).

| Area | Endpoints |
|---|---|
| Runs | `POST /api/runs` (multipart files or zips → **202 Accepted**), `GET /api/runs`, `GET /api/runs/{id}`, `GET /api/runs/{id}/progress`, `POST /api/runs/{id}/reanalyze`, `DELETE /api/runs/{id}`, `POST /api/demo` |
| Results | `GET .../issues`, `GET .../issues/{id}`, `GET .../tests?status=&module=&issue_id=&q=&limit=&offset=`, `GET .../tests/{id}/log?around=&start=&lines=`, `GET .../tests/{id}/log/raw`, `GET .../modules` |
| Workflow | `GET /api/compare?base=&head=`, `GET/PUT /api/signatures/{sig}/triage`, `GET .../export?format=csv\|json\|markdown` |

### Design choices
- **Uploads are asynchronous.** `POST /api/runs` stores files, queues a job, and returns 202 with the
  run. Clients poll `/progress`. No request ever waits for analysis.
- **Triage belongs to the signature, not the run.** A note like "known issue, JIRA-42" made on Monday's
  run appears automatically on Tuesday's run when the same problem recurs. This is the basis for the
  known-issue library in Phase 8.
- **Comparison matches signatures:** issues are new, recurring, or resolved by signature id, which is
  stable across runs and simulators (ADR 0006).
- **The log viewer returns a window**, by default centered on the root cause, plus every error line in
  the file, so the UI can offer "jump to next error" without loading multi-megabyte logs.
- **Errors are written for people:**
  - 400 for bad uploads ("setup.exe: not a log file"), 404 for missing things.
  - **409** when results are requested before analysis finishes ("Analysis is still running."). This
    is distinct from 404 because the client should wait, not give up.
  - 413 for oversized uploads, rejected from the `Content-Length` header before the body is read.
- **One service layer:** routes are thin. Queries live in `services/results.py` and `services/runs.py`,
  which the HTML pages reuse. Exports rebuild the engine's own report object from stored rows, so
  Markdown/JSON exports and the CLI's output stay identical in format.
- **Paging** uses `limit`/`offset` with a `total`. Tests list failing ones first, so page one is
  always the interesting page.

## Alternatives considered
- **GraphQL:** flexible queries, but more machinery for a small, well-known set of screens.
- **WebSockets / server-sent events for progress:** smoother, but polling a lightweight endpoint
  every second is simpler, works through every proxy, and is easy to test. The worker throttles its
  progress writes to match.
- **API versioning (`/api/v1`):** not needed while the API and its only UI ship together in one image.

## Testing
End-to-end API tests drive the real stack against Postgres: zip upload → worker → issues, tests,
log window, modules, triage, CSV/JSON/Markdown export, delete. Compare is checked against the
dataset's bug lifecycle, and error cases are covered (not ready, missing, bad upload, oversized). A
live run against the Docker stack produced the comparison that exposed the signature-identity bug
described in ADR 0006.
